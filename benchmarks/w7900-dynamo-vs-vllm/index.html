Dynamo vs plain vLLM on the Radeon PRO W7900

Same vLLM 0.33.0 ROCm engine underneath, measured two ways on one GPU: vLLM's own OpenAI server, and NVIDIA Dynamo's frontend plus vLLM worker built by Open Inference Fabric for AMD GPUs. Quick profile, one repeat, 7 November 2026.

GPU Radeon PRO W7900 (gfx1100, 48 GB) · torch 2.13.0 + ROCm 10.0 · vLLM 0.33.0 · Dynamo 1.7.0 · AIPerf 0.13.0 · 24 of 24 points, 0 errors
Output throughput
±0.4%

Dynamo matched vLLM at every point: from 0.0% to +0.4% on both models, both workloads, concurrency 1 to 32.

Time per output token
≤1.4%

Generation speed per user was the same. The largest gap was 9.04 vs 9.17 ms (0.6B chat, 32 users).

Time to first token
up to −40%

Dynamo returned the first token sooner when prompts are short or the model is small: 9 to 53 ms less at 8 and 32 users. No gain where prefill fills the GPU (8B, 512-token chat).

Reading the results

  • Dynamo adds no measurable cost to generation on one GPU. Throughput and time per output token stayed within 1.4% at all 12 paired points.
  • The first-token gain is consistent. It shows up at 8 and 32 users for both models on short prompts, and for 0.6B on 512-token prompts. The next section explains where it comes from.
  • Where prefill dominates, both are equal. Qwen3-8B with 512-token prompts at 8 and 32 users waits 0.65 to 1.05 s for the first token on both stacks: the GPU itself is the queue.
  • What this test does not cover. Dynamo's main features (KV-aware routing across workers, prefill/decode disaggregation, the planner) need several GPUs. This run only answers whether the Dynamo layer costs anything on one card.

Why Dynamo gets the first token out sooner

Nothing in Open Inference Fabric's ROCm build changes how Dynamo handles a request: the build only packages Dynamo for AMD GPUs. The gain comes from how Dynamo divides the work around the same vLLM engine. Both stacks run vLLM's engine core (scheduler and GPU work) in its own process; what differs is the work done before a request reaches it and after tokens leave it.

Step for every requestvLLM's own serverDynamo + vLLM
Accept the HTTP request, parse the OpenAI JSONPython (FastAPI) in vLLM's API server processRust frontend (dynamo.frontend), multithreaded
Apply the chat templatePython, in that same processRust (Dynamo preprocessor)
Tokenize the promptPython calling the Hugging Face tokenizer, same processRust, with a tokenizer cache
Hand the request to the engineIn processToken IDs over Dynamo's TCP request plane to the dynamo.vllm worker, which passes them to vLLM as a TokensPrompt
Prefill and decode on the GPUIdentical: the same vLLM 0.33.0 engine core, arguments and kernels
Turn tokens back into text, stream to the clientPython incremental detokenizer and SSE, in the API server processWorker sets detokenize = False; the Rust frontend detokenizes and streams
  • Why it helps first-token time. With vLLM's own server, one Python event loop does the per-request text work for every user: templating and tokenizing new requests while it also detokenizes and streams tokens for the requests already running. Under load a new request waits its turn in that loop before the scheduler sees it. Dynamo does that work in Rust on several threads, so a new request reaches vLLM's scheduler sooner. The saving is host-side time, which is why it grows with the number of users (8 and 32) and matters most when GPU prefill is short (128-token prompts, or the small 0.6B model).
  • Why throughput and time per token do not change. Once a request is running, each decode step is GPU work done by the same engine core. Moving text handling out of the Python process does not make the GPU faster.
  • Why the gain disappears for 8B chat at 8 and 32 users. There the first token waits 0.65–1.05 s for prefill of other users' 512-token prompts on the GPU; tens of milliseconds saved on the host are lost in that queue.
  • What we have not explained yet. 8B decode with a single user was also 18 ms faster with Dynamo (59 vs 41 ms), where queueing in the Python loop should be small. Per-stage timings (frontend, queue, prefill) are planned with the full run before we claim more.

Source: ai-dynamo/dynamo, components/src/dynamo/vllm (TokensPrompt, detokenize = False) and lib/llm/src/preprocessor (template, tokenize) on the OIF rocm branch.

Run quality

  • 24 of 24 points completed, 0 request errors, 0 server restarts.
  • Output length matched the request on 22 points. Qwen3-0.6B decode produced 1,012–1,017 tokens of the requested 1,024 (0.7–1.2% short) on both stacks equally, so the comparison holds.
  • One repeat: no run-to-run spread yet. The full profile (4 workloads, concurrency 1–64, 3 repeats) gives p90/p99 latencies and a noise verdict per point.
