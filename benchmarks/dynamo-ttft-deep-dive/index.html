Why Dynamo's first token comes sooner than vLLM's own server

In our W7900 benchmark NVIDIA Dynamo served the same vLLM engine with the first token up to 40% sooner, at the same throughput. We traced where that time goes, on an AMD Radeon PRO W7900 and an NVIDIA RTX A6000 in the same machine. The gap is the same on both GPUs, and it is not in the GPU or the engine: it is in how vLLM's single API process hands each first token back to the user. vLLM's own options close most of it.

    How the first token travels

    The engine core runs the model and is the same in every stack. What differs is the process that turns the engine's output into the response. In plain vLLM one Python process does everything for every user: HTTP, chat template, tokenizing, and the output processor that receives each step's tokens from the engine core, detokenizes them and streams them out. Dynamo moves HTTP and tokenizing into a Rust frontend and runs the output processing in a worker process of its own.

    vLLM's API process is not maxed out: it uses 40 to 65% of one core even at 64 users. The cost is waiting inside that one process, not a lack of CPU. Profiles put most of its samples in thread-pool workers next to the event loop; contention for Python's global lock between them is our working explanation, not yet a measured one.

    What it means

    • It is not an AMD or ROCm problem. The same milliseconds appear on CUDA and on ROCm, on the same host CPU, because the API process is the same Python code on both. Asking for a ROCm fix would aim at the wrong place.
    • If you run vLLM's own server, start it with --api-server-count above 1, or try its experimental Rust frontend (VLLM_USE_RUST_FRONTEND=1). Both closed most of the gap here, on both GPUs.
    • Dynamo's lead is a front-end lead. It shows with many users and a small, fast model, where the GPU work per token is short. With one user it is small, and vLLM's Rust frontend was faster still.
    • Throughput is not the story: tokens per second and time between tokens are equal within 2%.

    Still open

    • At 64 users plain vLLM on the A6000 is faster than at 32 (short prompts: 34 ms, below Dynamo's 39). The W7900 does not show it. A guess, not checked: the faster GPU finishes the fixed-length answers in step, so new requests arrive in waves and are prefilled together.
    • vLLM's Rust frontend at 64 users on the W7900: the engine core's own time jumps to 77 ms, as if requests are handed over in bursts.
    • One small model (Qwen3-0.6B). With an 8B model the GPU's share grows and the gap should shrink; not traced yet.

    Method and data

    One lab machine, both GPUs on the same host CPUs, run one after the other, never at the same time. vLLM 0.33.0 from vLLM's own images (vllm-openai-rocm, vllm-openai); Dynamo 1.7.0 built by Open Inference Fabric from one source commit for both GPUs, each on top of the matching vLLM image. Load from AIPerf 0.13.0 at a fixed number of users, 60 seconds per point after a warm-up, exact output lengths, GPU cooled below 60 °C before each point. Timings from 3 repeats; the time split from one traced repeat with py-spy, CPU sampling and vLLM's own metrics. Every point checks that no other program uses the GPU; the runs here had none and no failed requests.

    Stacks: vLLM (vllm serve), vLLM ×4 API (--api-server-count 4), vLLM Rust frontend (VLLM_USE_RUST_FRONTEND=1), Dynamo (Rust frontend and a dynamo.vllm worker).
